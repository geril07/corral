# Design

A keyboard-first workspace for running coding agents, for people who live in the terminal.
Replaces Herdr for its author; Orca and T3 Code are references, not bases.

Kind: **product decisions**. A later decision in this file supersedes an earlier one; when it is
silent, the code decides and this file is corrected rather than read as a spec.
Client UI rules: `ux.md`.

## Architecture

```
 desktop client (Electron, xterm.js)  ─┐
 mobile client (later)                ─┼─ WebSocket ── server (Node)
 client on another machine (later)    ─┘                ├─ tasks, sessions store
                                                         ├─ git worktrees
                                                         ├─ PTY manager (node-pty)
                                                         ├─ agent status ingest
                                                         └─ agent protocol adapters (chat)
```

- **Server** is a separate long-lived process. The desktop app starts it if none is running, and it outlives the window, like Orca's daemon.
- **Terminal streams** go as binary frames with ack-based backpressure.
- **Reattach**: the server feeds every PTY into an `@xterm/headless` instance (scrollback ~5k rows, as Orca and T3 Code) and sends a serialized snapshot, then live output. Normal-buffer scrollback and the alt screen are serialized separately (Orca's `terminal-snapshot.ts` is the reference).
- **Server lifecycle**: detached process, single-instance lock, PID/endpoint file, versioned handshake so an old client and a new server refuse to talk instead of misbehaving. Orca and T3 Code both hit duplicate-instance and update-skew bugs (`.refs/t3code/docs/architecture/server-updates.md`).
- **One API** for every client. Nothing desktop-only in the protocol, so the mobile client is just another client.
- **Web client** is the same bundle in Electron and in a plain browser served by the server. Electron adds only native shell bits (window, menus, starting the server).
- **Mobile** (roadmap): another client of the same API. The UI framework choice must leave a realistic mobile path (open question).
- **Remote**: a client connects to a server on another machine. This needs auth and a transport beyond loopback; out of MVP, but the protocol must not assume localhost.

### Local trust boundary

The server executes commands for its clients (`terminals.create` takes command, args and env), so a web page on another origin that can reach loopback must not become a client. Each server run generates a random capability (32 bytes, base64url) and publishes it only in `endpoint.json` in its state directory (`0700` directory, `0600` file). Every WebSocket presents it as a subprotocol (a `corral.capability` marker followed by the token), and the single upgrade handler checks it before choosing `/rpc` or a terminal path; a missing or wrong capability gets HTTP 401 and never reaches routing. The token is never put in a URL, so request logs, `Referer` and diagnostics stay clean. `Origin` is not the gate: desktop loads `file://`, browser dev loads another origin, and `Origin: null` is common, while any holder of the capability is trusted.

Delivery: the desktop main process reads the endpoint file for every IPC request and hands `{url, capability}` to the page over a narrow preload IPC bridge, only to the trusted top frame; other frames and popups get nothing. The page URL keeps only the tokenless `?server=`, unexpected navigation is blocked, and ordinary http(s) links are passed to the OS browser instead of loading in the capability-bearing window — chat's rendered links ask the shell for that over the same preload bridge (`corral:open-external`), and the shell re-validates the scheme before `shell.openExternal`. A local file link in chat is not a URL: its bytes come from the task's workspace over RPC, bounded, `realpath`-checked and read from the inode the check saw (`docs/engineering.md`), never through a page URL or a file association. It is rendered as an inline action rather than an anchor, because a link that runs the editor cannot honour a copied or middle-clicked URL. Clients ask for the current target before each reconnect, so a server restart with a new capability recovers without quitting the app. Browser/dev mode takes an explicit capability from `#/route?capability=...`, keeps the URL and capability together in `sessionStorage` and removes it from the hash before routing. A stored pair is only used for its own server URL, so a `?server=` redirect cannot receive it; a new explicit hash bootstrap replaces the pair. Browser reloads and hash navigation work; a page with no capability shows a startup error instead of opening an unauthenticated socket, and a disconnected one points to the explicit refresh path.

What this stops: a hostile page that can reach loopback calling RPC (including `terminals.create`) or attaching terminal streams. What it does not stop: code already running as the same OS user, which can read `endpoint.json`; that code is trusted like the config file. Status reports keep their separate per-session bearer token, and remote authentication/RBAC stays out of MVP (see **Remote** above).

**The agent's own server is the same case.** OpenCode 2.2.5's `opencode serve` binds loopback and generates a per-server password; `/api/*` answers `401` without credentials and HTTP Basic `opencode:<password>` is the accepted form (measured, `.e2e/stage-c/c1/probe/`). Corral starts one server per run with `--hostname 127.0.0.1 --port 0`, exports the password it read from the server to every client it launches (`OPENCODE_SERVER_PASSWORD`), and never binds it elsewhere. No Corral capability token sits on top: the loopback bind is the boundary, and the password is per run rather than per session because one server serves the run's sessions. Code already running as the same OS user can read the password from the processes' environment, as it can read `endpoint.json`; that is the same trust assumption.

Codex 0.166.0's app-server follows the same rule with a filesystem boundary instead of a password, and the boundary is the real socket's, not the nice path's: `--listen unix://<dataDir>/codex/<session>.sock` writes a **symlink** at that path into `/tmp/codex-daemon-<uid>/<hash>`, where the listening socket itself is `0600` in a `0700` per-user directory. The symlink's directory is the server's data directory, which Corral creates and chmods `0700` (`codex-server.ts`); the path is a name for the socket, not a second copy of it, so anyone who can write that directory can redirect the name, which is the same trust as `endpoint.json`'s. The protocol carries no in-band auth; Corral never opens a `ws://` port (a ws listener would need `--ws-auth capability-token`) and passes no approval or sandbox bypass. Code running as the same OS user can open the socket; that is the same assumption as `endpoint.json`.

## Domain model

- **Project**: a git repository, added by path. The server trims the input, expands a leading `~` with its own home and requires an absolute path; a relative path is refused. The stored `Project.path` is git's absolute main working tree, so a subdirectory, symlink or linked worktree names the one project.
- **Task**: title, state (active / settled), workspace, optional branch. Settled means the work is done (T3 Code's "settle"): the task moves to a collapsed shelf, keeps its worktree and branch, and its running sessions are stopped; making it active again resumes the sessions that were running. A merged pull request **offers** settle on the task (`layout.md`, **Changes**); the click is still the user's, and automatic settling (merged, inactivity) comes later.
  - **Creation**: the new-task composer takes a prompt plus project, agent or launch profile, an optional native model override, view (chat by default, or terminal) and workspace, all prefilled from settings. Submitting creates the task and starts its primary agent session with the prompt (the TUI receives it as its launch argument); no shell starts on its own. A task can also start without a prompt; it then keeps a placeholder title until it is renamed or named from the agent's first message.
  - **Workspace**: the project's main working tree by default; a new worktree (new or existing branch, off the project's default branch) is an option chosen in the composer or made the default in settings. The branch list offers only targets a worktree can check out: local branches no worktree of the project holds (the main tree included), and remote-tracking refs whose derived local branch is neither held nor in conflict with a local branch above or below it. Task creation reads the worktree list again before `git worktree add`; a branch taken since the list was read is refused by name and the path that holds it, and the composer keeps the draft.
  - **Naming** (decision 16): the seed title is the normalized, truncated prompt and shows immediately; the generated title replaces it. Slug mode is a setting: `title` (branch and worktree slugs derived deterministically from the generated title) or `generated` (one request returns title, branch name and worktree name). In worktree mode the worktree is created after naming, with a timeout, so a random name never reaches disk (T3 Code creates `t3/<random>` first and its directory keeps that name after the branch is renamed). Branch: `<prefix><slug>`, where the prefix comes from settings, is empty by default and ends in `/` (a missing separator is added). Name collisions get `-2`, `-3`. The title can be renamed; renaming does not move the worktree or rename the branch. The task keeps where its title came from (`seed`, `generated` or `user`), so a later naming result never replaces a title the user typed. OpenCode cannot be the naming runner: its non-interactive `run` always saves a session (2.2.5), so `[naming]` refuses it with a config problem. Codex has no flag that removes its read-only tools: naming ignores the user's config and execpolicy rules (so the user's MCP servers and hooks do not run), runs in a read-only sandbox with approvals disabled (no shell writes, no approval prompts), and can still read whatever the server's user can read.
  - Worktrees live at `<worktree root>/<repo>/<slug>`. The root defaults to `<data dir>/worktrees` (`~/.local/share/corral/worktrees`), so worktrees never show up in the user's repository directory, and is configurable; Herdr uses the same `<root>/<repo>/<branch-slug>` layout and lists any git worktree of a repo, so a shared root keeps both tools' checkouts together and readable. `<repo>` is the repository's directory name with no project id in it, so two projects with the same directory name share `<root>/<repo>/`; their slugs are told apart by the same `-2`, `-3` suffixes as before when they collide, a readable path being worth more than naming the project on disk.
  - Removing a task closes its terminals and removes the worktree it owns, but refuses a worktree with uncommitted or untracked changes unless forced. Branches are never deleted by Corral.
  - Projects and tasks persist in SQLite (`<data dir>/corral.db`); terminals do not (decision 12).
  - A task can keep an immutable GitHub/GitLab issue-source snapshot: original title, body and link. Import reads through the user's CLI in the chosen project; editing the draft task title does not rewrite the source. An answer whose URL is a pull request is refused as a pull request, not as an unreadable issue, and the composer keeps the pasted URL. No remote writes or synchronization are implied. Scope and trust rules: `research/integrations.md`.
- **Session**: lives in a task. Either a shell, or an agent session `{ agent, agentSessionId, view: terminal | chat }`. A task may hold any number of agent sessions; the one created from the prompt is **primary**: the task's title and default chat come from it.
- **Space**: an optional saved grouping or filter over tasks, not a container.
- **Board**: all tasks with their status, navigable from the keyboard.

A task's status comes from its agent sessions (working / blocked / done / error / idle).

### Sessions

- Everything that runs in a task is a session: a shell or an agent (Claude Code, Codex, pi, OpenCode). Sessions persist; terminals do not. A loose terminal outside any task is the only kind that is not a session.
- After a server restart, sessions that were running start again: a shell fresh in the workspace, an agent resumed by its own session id. A session the user stopped, or an agent that exited by itself, stays stopped until started again.
- The prompt a task was created from (**Domain model → Task → Creation**) is the session's launch argument on its first start: the adapter's `promptArgs` puts it on argv as a single word, never through a shell, shaped so the agent reads it as a prompt and not as a flag or one of its own subcommands. All four dispatch elsewhere on that word: Claude Code and Codex run the first operand as a subcommand (`claude mcp`, `codex review`), so Codex always gets the prompt after `--`, where clap reads every later word as a positional, while Claude Code always gets one leading space, because `--` does not help there — its commander parser keeps the words after `--` as operands and dispatches on those too. pi's first argument is always one of our flags, so only its first character matters: `--` for a leading `-`, and one leading space for a leading `@`, which pi would otherwise read as a file to include even after `--`. OpenCode takes the prompt as a flag value, `--prompt <text>`, attached as `--prompt=<text>` when the text starts with `-`.
- Restart, settle → continue and a server-restart restore resume the conversation and do not pass the prompt again, or the agent would redo the work. A start that failed before Claude Code wrote its transcript leaves nothing to resume, so a restart falls back to a new conversation under the same id; that fallback may carry the prompt when the caller offers it again, which is the caller's decision — the launch stores no prompt text. A shell takes no prompt; asking for one is an error, not a silent drop.
- Agent session ids, checked against `--help` of the versions in the table below:
  - Claude Code: `--session-id <uuid>` at start, `--resume <uuid>` to resume. pi: `--session-id <id>` both ways (creates it if missing). OpenCode: `--session <id>` both ways (creates it if missing).
  - Codex cannot be given an id. Herdr and Orca learn it from a `SessionStart` hook they install in the user's global `~/.codex/hooks.json`. Corral does not touch global agent config in MVP; instead the server finds the new rollout file in `$CODEX_HOME/sessions` whose `session_meta.cwd` is the task's workspace and that started after the spawn (workaround: two Codex sessions started at once in one workspace are ambiguous). Resume: `codex resume <id>`.
- Agents get `CORRAL_SESSION_ID` and `CORRAL_TASK_ID` in their environment, plus `CORRAL_STATUS_URL` and `CORRAL_STATUS_TOKEN` for agents that report status over HTTP.
- **Launch profiles** in `config.toml` name an agent, optionally a native model/provider and environment references, so a new session can choose a provider without Corral holding credentials. The nonsecret choices are snapshotted on the session; referenced values are resolved from the server environment at launch. This is explicit overrides, not account isolation or a sandbox. `[agents.<kind>]` beside them only says whether Corral offers the agent (`enabled`) and which executable a launch runs (`command`); model, provider and environment stay in the profile. Config, capability rules and security promises: `docs/agent-profiles.md`.

### Status

- The server's headless terminal parses OSC 7501 and answers its `?` probe (Claude Code and pi only report after the probe). A session's status is its root record; a blocked subagent makes the session blocked.
- OpenCode 2.2.5's TUI answers the OSC 7501 `?` probe and reports `\x1b]7501;state=idle:app=opencode` (measured in a PTY against a server Corral started, `.e2e/stage-c/c1/probe/`). That is now the OpenCode terminal view's status channel: a server-backed TUI needs no plugin.
- OpenCode still has a plugin (`opencode-plugin/index.js`, derived from Herdr's v2 plugin API, POSTing to `CORRAL_STATUS_URL`). It is loaded only when an OpenCode TUI could not attach to the run's server and fell back to `opencode --standalone` (server in the client process), where plugins see that session's environment. A server-backed session does not load it: one server serves many sessions, the plugin has no per-session token, and chat sessions take their status from the event stream instead. Once a launch has delivered an HTTP report, OSC no longer changes that session's status until the next launch (Orca's rule, without Orca's 2-minute takeover when the plugin goes quiet).
- A task's status is the most urgent of its sessions': blocked, error, working, done, idle.
- A task's `seenAt` is when the user last looked at its agent updates, stored by the server
  (not in client storage) so every client agrees: a `done` update newer than it is completed
  and unseen, and opening the task or watching it while its status changes clears the mark.
- Board: all active tasks across projects with their status and the agent's message, most urgent first, opened from the keyboard; choosing a task jumps to the session that needs attention.

## Agent status

- **OSC 7501** (Program Status Protocol): parse via `term.parser.registerOscHandler(7501, …)` and answer the `?` probe. Support matrix: `.refs/orca/src/main/agent-hooks/README.md`.
  - Claude Code, pi, Grok: state, blocked reason, message. Codex: state only.
  - Parsing belongs on the server, so status works with no client attached.
- **OpenCode**: plugin that reports session events to the server. Port from Herdr, Apache-2.0: `.refs/herdr/src/integration/assets/opencode/herdr-agent-state.js` (~220 lines).
- **Not now**: Orca's full hook layer (~21k lines) and Herdr's screen-scraping manifests (`.refs/herdr/src/detect/manifests/`). Revisit only for an agent with neither OSC 7501 nor a plugin API.

## Terminal and chat

Verified by research for Claude Code 2.1.316, pi 1.4.0 and OpenCode 2.1.4 (docs and source; nothing run), and by measurement on this machine for OpenCode 2.2.5 and Codex 0.166.0 (`.e2e/stage-c/c1/probe/`, `.e2e/stage-c/c3/probe/`: each probe ran under a temporary `HOME`/`CODEX_HOME` against a local Responses stub, never a real model turn). All four store sessions by id and resume them from both the TUI and the programmatic mode, so switching view = stop one frontend, resume the same id in the other. What survives is the stored history; in-flight turns, pending approvals and streaming state do not — except where the agent's own server keeps them, which is what the two `both-live` rows below use.

| Agent       | Session id                                                                | Chat via                                           | History for the chat view                                 | Two frontends live at once                                                                                                                                                               |
| ----------- | ------------------------------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | we set it: `--session-id UUID`; resume `--resume ID`                      | Agent SDK (`options.sessionId` / `options.resume`) | SDK `getSessionMessages()` (transcript JSONL is internal) | no (`handoff-only`); `claude attach` is for its own `--bg` sessions                                                                                                                      |
| Codex       | server assigns it (`thread/start` takes no id); the app-server reports it | app-server over its unix socket                    | `thread/resume` / `thread/read` (turns and items)         | yes, when both are clients of one app-server (`--remote unix://…`); a TUI on its own daemon is read-only beside it, and a second app-server gets `thread … already has an active writer` |
| pi          | we set it: `--session-id ID`                                              | `--mode rpc`                                       | RPC `get_messages`                                        | no; no writer lock, concurrent appends corrupt the file                                                                                                                                  |
| OpenCode    | we set it: `--session ID`                                                 | its HTTP server                                    | `GET /session/:id/message`                                | yes, as clients of one server                                                                                                                                                            |

Rules this implies: one writer per agent session at a time, enforced by our server; for Codex and OpenCode the agent's own server is the live session and both views attach to it.

- **Codex, measured 0.166.0: `both-live`, but only as clients of one app-server.** Corral runs one `codex app-server --listen unix://<dataDir>/codex/<session>.sock` per session; the chat driver is a JSON-RPC client of that socket and the terminal view is `codex --remote unix://… resume <thread>` in the same `CODEX_HOME`. With both attached, the TUI accepted input and its turn streamed into the chat client, a `turn/start` from the chat appeared in the TUI, and `canAcceptDirectInput` stayed `true` on the thread for both. The unix listener is a **WebSocket** endpoint (a plain `GET` upgrade answers `HTTP/1.1 101`), not newline JSON-RPC — `--stdio` is the newline transport, at the cost of having no attachable socket. Approvals are server→client JSON-RPC requests (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, and the legacy `applyPatchApproval`/`execCommandApproval`) sent to **every** attached client; one `{decision}` from any of them produces `serverRequest/resolved` for all, so the first answer wins and the others mark the request resolved instead of asking again. The two-client measurement used two JSON-RPC clients; that the TUI's own dialog is the one answering first (and the chat item resolving) is C-verify's check, though the TUI and the driver receive the same request. Requests this client does not render (a permissions profile, an MCP elicitation, a tool call, an approval whose decisions are all object-valued) are left to the terminal's dialog while a terminal leg is live, because the first answer wins; in a chat-only session there is nobody else, so the driver answers with an error result and shows a visible line instead of leaving the turn parked. Commands and outputs: `.e2e/stage-c/c3/probe/README.md`.
- **The plain TUI is the external writer, and stage A's launch leaves a daemon.** `codex` with no `--remote` auto-starts a managed app-server under `$CODEX_HOME/packages/app-server-daemon/` (`daemon_auto_start stable true`): after the TUI quit, two processes and `app-server-control/` plus `app-server-daemon/` sockets stayed in the isolated home. A thread another app-server holds opens there read-only — "This conversation is open in another app / Close it there and press R to continue here" — and a second `codex app-server` on the same `CODEX_HOME` refuses `thread/resume` with `thread <id> already has an active writer`. `--no-daemon` starts nothing extra (measured: no process left after quit) but has no socket to attach to. Corral therefore gives **every** tested-version Codex session its own app-server and launches its terminal with `--remote`, so a later view switch is live and no Corral-launched TUI leaves a managed daemon behind; stage A's plain launch remains only for an untested CLI or a session whose server could not start while no chat frontend is live. When the app-server dies under a live terminal, the TUI shows "Reconnecting to server…" for as long as it is left alone (measured, `.e2e/stage-c/c3/probe/tui-remote-server-lost.txt`), so the server closes that terminal leg and settles the session instead.
- **The thread id is the server's; the prompt is sent only into an empty conversation.** `thread/start` has no caller-chosen id in the generated 0.166.0 schema, so the driver reports the id it gets (`onAgentSessionId`) and `Session.agentSessionId` stores it; a rebuild is `thread/resume` (which subscribes that connection to the thread's events) plus `thread/read` when the resume carried no turns. A thread the terminal created in the session's app-server is adopted from `thread/list`. A user message is sent with `clientUserMessageId` and echoed with that value in `clientId`, so a rebuild replaces the optimistic item instead of duplicating it — and a conversation that already has a user message never receives the task prompt again. `thread/queue/add` (follow-up) requires the app-server's `experimentalApi` capability, measured and refused without it, so the Codex driver declares `followUp: false` instead of opting into that surface for one call.
- **Claude Code, stop-and-resume only, and the SDK uses the user's own install and login** (C2, measured on 2.1.316 through `@anthropic-ai/claude-agent-sdk` 0.3.316). No supported live attach between the SDK and the TUI: `claude attach` is for its own `--bg` sessions, and Remote Control goes through claude.ai, so it is out. Corral runs the user's `claude` — `[agents.claude].command` or `PATH` — as `pathToClaudeCodeExecutable`, never the SDK's bundled platform copy (installed without its 328 MB optional packages), and a version gate refuses chat with a visible sentence on anything but 2.1.316, leaving the terminal available. A no-turn probe of the user's login reported `firstParty` / `Claude Pro` and five models with `low…max` effort (`.e2e/stage-c/c2/probe/`); that probe created a `session-env/<uuid>/` directory under `~/.claude`, so chat is not config-dir-neutral even with no turn, and tests keep `CLAUDE_CONFIG_DIR` isolated. The SDK spawns the CLI as a subprocess, so the SDK and the TUI cannot share one session: `prefix v` keeps B4's serial stop-and-start and the terminal leg is `claude --resume <id>`. Permissions are the contract's user requests one-for-one (`toolUseID` names the request), model and effort lists come from `supportedModels()`, and the transcript stays the agent's own JSONL.

### The chat contract

`packages/protocol/src/chat.ts` is Corral's own, provider-neutral chat shape (decision 14): items with stable ids (user and assistant messages, reasoning, tool calls with an optional diff, user requests, notices, errors) and session-level state (turn, queued steering and follow-up messages, the current and available models, the reasoning level and levels). The server owns that state and streams it as one snapshot plus sequenced events; a client that reconnects with its last sequence gets the missing events, or a fresh snapshot when they are gone. `chat.send` (prompt, steer, follow-up), `chat.abort`, `chat.respond`, `chat.setModel` and `chat.setReasoning` are the only writes, and `chat.capabilities` says which agents this build can show as chat and what each driver declared about itself. A `plan` item joins when a driver emits one, with protocol 10: decision 14 still lists it, and adding an item kind is a wire change. No client sees a provider protocol, and the contract keeps no transcript of its own: the agent's own session is the conversation.

Each chat agent is one implementation of a server-side interface, extracted from the working pi driver (C0). `apps/server/src/chat/chat-driver.ts` holds `ChatDriver` — what the service calls (`start`, `stop`, `closed`, `sessionId`, `state`, `timeline`, `send`, `abort`, `respond`, `setModel`, `setReasoning`) plus its launch inputs (`timeline`, `command`, `args`, `cwd`, `env`, `prompt`, `writer`) and the callbacks it raises (`onStatus`, `onExit(reason | null)`) — and `chat-drivers.ts` is the registry, `kind → { capabilities, args, create }`. Two things are split on purpose. The chat argv is the driver's, so the session service knows no agent's flags. The single launch claim, the timeline (its start is the reserved sequence floor), the persisted writer record (the service writes it from the pid the driver reports, through a `record`/`release` pair, and keeps its path and pid identity) and the `CHAT_UNAVAILABLE` vocabulary are Corral's and stay in `ChatService`: a driver cannot pick its floor or forge a refusal code, though it does choose which `chat-errors.ts` class a failed operation raises and what sentence that refusal carries. `chat.capabilities` answers from that registry with the per-driver record — `steer`, `followUp`, `approvals`, `modelSwitch`, `reasoningLevels`, and the terminal a session can have next to chat: `both-live`, `view-only-terminal` or `handoff-only`. pi is `handoff-only`, because pi has no writer lock. The record is on the wire so a control is offered only where a driver declared it; the chat composer reads `steer`/`followUp`, and C1's both-live action reads `terminalView`.

### The pi driver (stage B, B1)

A session row carries a view (`terminal` or `chat`), persisted by migration 9; every session from before it is a terminal. A `chat` session has no PTY: its live frontend is `pi --mode rpc --session-id <id>` in the task's workspace, with the launch arguments, profile environment and `CORRAL_*` variables a terminal launch gets. Starting, stopping, settling, continuing and restoring a chat session go through the same session service as a terminal one, so a server restart resumes the same pi session in the same view.

- **One writer.** pi has no session-file lock, so a session has at most one live frontend by construction: the driver never starts a second child on one id. Each child's pid is recorded; a server that starts again kills the recorded process (or waits for it to go) before it spawns its own. Closing stdin is enough in the normal case: pi 1.4.0 exits on stdin EOF even mid-turn (measured).
- **The chat is rebuilt, not stored.** On every start the driver asks pi for `get_messages` and its model state and turns them into items, then streams events. Pending dialog requests and in-flight streaming do not survive a restart; that is the same limit as a view handoff.
- **The prompt of a chat task** is sent with the `prompt` command once the child is ready, and only when pi's own history has no user message. A resume therefore never repeats it, and a start that died before pi wrote it hands it over again.
- **Status comes from events**, not OSC 7501: `agent_start` is working, a pending dialog is blocked (`question`), `agent_settled` is done (idle when aborted), a provider error is error, and a failed frontend keeps an error status plus the reason in `launchError`. Settling the _task_ stops the child (the run keeps going only if the user settles it); `agent_settled` is pi's "the run will not continue by itself", not that action.
- **During a run**, `chat.send` with `prompt` is refused by pi: the client steers the running turn (`mode: "steer"`) or queues after it (`mode: "follow-up"`) and the composer chooses by turn state (B3). The refusal, should a client send anyway, is one visible error item and changes nothing else.
- **Dialogs** are server-expired on a deadline (10 minutes, shorter when pi's extension set its own timeout), because pi resolves its own timeouts locally and the contract cannot rely on an event for that. Answering, dismissing, expiring, aborting and stopping all replace the request item in place.
- **A tool diff** is pi's unified patch from the tool result (`details.patch` of `edit`, path from the call's arguments), not its compact `details.diff`; a tool result without one has no diff.

### The handoff between views (stage B, B4)

`prefix v` (`sessions.setView`) moves one session between chat and terminal. It is a serial stop and start, not two frontends:

- A working turn of a **chat** frontend is aborted first — pi is sent `abort`, any dialog waiting for an answer is cancelled, and the turn gets the grace a stop gives to report it ended, so a turn pi closes stays in the conversation. A terminal has no abort channel: closing its PTY is what ends its turn, so what pi had not written is lost, and the confirmation says so per direction. The abort itself is bounded by the same grace, so a pi that is alive but silent costs that grace instead of parking the session's queue. Then the live frontend is stopped through the same path a plain stop uses: a chat child closes stdin, is waited for and killed with its group; a terminal's PTY is closed and awaited. Only then does the other view start, with `--session-id`/`--resume` on the same agent session id. One writer exists at every moment. The fake pi checks that at the boundary — it writes an overlap marker if a second frontend of one session id starts while the previous one is alive, and the handoff tests assert the marker never appears — while the real pi contract's TUI leg only waits for the PTY to exit before the driver starts: an awaited exit, not a marker.
- The session is never recreated, so its id, label and tab position stay; only `sessions.view` changes, and it is persisted, so a restore opens the view the user last chose.
- In-flight state does not survive (it cannot, per the table above), so the client confirms while the agent is busy: the confirmation says what happens to the turn and to a pending request (aborted for chat, cut with the terminal), and that the conversation stays. When the agent is idle the switch runs at once, and while it runs the main area says so rather than showing a half-switched pane.
- A failed second start leaves the session `stopped` in the target view with its `launchError`; `restart` (or `prefix v` back) is the retry. On a stopped session `setView` only records the view its next start opens in.
- The offer is a build fact, not a client guess: the palette asks `chat.capabilities` and shows the action disabled with the reason for a shell or an agent this build cannot show as chat. The record also says how a terminal can exist beside the chat (`both-live`, `view-only-terminal`, `handoff-only`), which is what tells `prefix v` whether a handoff is the right action (C1).

### The OpenCode driver (stage C, C1)

OpenCode is the first `both-live` driver: the conversation lives in one `opencode serve`, and both frontends are clients of it.

- **One server per Corral run, started lazily and stopped with its last client.** `OpenCodeServers` (`apps/server/src/chat/opencode-server.ts`) spawns `opencode serve --hostname 127.0.0.1 --port 0`, reads `server listening on …` and `server password …` from stdout, and keeps a process-keyed record at `<dataDir>/chat/opencode-server.json` (pid and `/proc` start time, written by `writer-claim.ts`). A Corral that starts again stops that server before spawning its own, so a second server on one data directory is never left running. Sessions and their terminal legs are counted as clients, so stopping one session leaves the server for the others, and the last stop ends it. `SessionService` owns the pool and gives both legs the same address.
- **Session ids stay Corral's.** The driver creates the session with `Session.agentSessionId` and `location.directory` = the task's workspace; `POST /api/session` accepts a caller-chosen `ses_…` id (measured). A server that restarted without the session re-creates it under that id, so settle/continue/restart keep one id and the terminal's `--session` names the same conversation.
- **The chat is an HTTP/SSE client.** `GET /api/event` is filtered to the session by `data.sessionID`; text, reasoning, tool calls and permission requests become the same items pi produces, and a user message from either frontend arrives as `session.inbox.enqueued` (its `inboxID` is the message id a rebuild reads), so a prompt typed in the TUI appears in the live chat as well as after a restart. Every (re)connect rebuilds the transcript from `GET /api/session/:id/message`, the path that works after a server restart, and OpenCode's own message and part ids are the item ids, so a rebuilt item replaces the streamed one instead of duplicating it.
- **Approvals** are `GET /api/session/:id/permission` plus `POST …/permission/:requestID/reply` (`once | always | reject`), shown as a `select` user request. An answer from either frontend resolves it once; the other frontend's answer arrives as `permission.replied`. `--auto` is never used.
- **Steer and follow-up** are the prompt's `delivery: "steer" | "queue"` (measured in 2.2.5's own schema). A `prompt` sent while a turn runs is refused visibly instead of being silently steered, because the composer offers steer/follow-up by turn state. Model and reasoning switching are declared unsupported, so the client hides those controls.
- **Both views at once, and what `prefix v` means.** The terminal attaches with `opencode --server <url> --session <id>` and `OPENCODE_SERVER_PASSWORD` in its environment. For a `both-live` driver `sessions.setView` therefore starts the target frontend **beside** the live one instead of stopping it: the session keeps one tab (its stored view says which frontend the main area shows), nothing is aborted and no confirmation is asked, and the palette says "Open the … view". A `handoff-only` driver keeps the serial stop-and-start unchanged. `chat.*` stays addressable while the main area shows the terminal, because the live driver answers whatever view the session currently shows.
- **The rendered pane follows `Session.view`, not the existence of a PTY.** `Session.terminalId` is the server's fact — a both-live session keeps its terminal alive while chat is shown — so the client tree attaches a session's terminal only in `view: "terminal"` (`packages/client/src/workspace-tree.ts`), and the main area renders the terminal only for a terminal view. Otherwise a live terminal would win forever after the first `prefix v` and the return path would show it instead of chat. The tab, sidebar and rename paths read the session's label and id, not the terminal, and keep working in either view.
- **One writer means one prompt writer.** The chat driver refuses a `prompt` while a turn runs (the composer offers steer/follow-up by turn state), and nothing else in Corral writes a prompt for that session. The terminal is a second _client_ of the same server, so the TUI can still type while a turn runs; OpenCode's own inbox admits what it sends — `delivery: steer` or `queue` — and that is the agent's rule, not Corral's. Corral cannot take the TUI's keyboard away and does not pretend to; what it can enforce is tested at the chat boundary (`opencode-driver.test.ts`), and the TUI's steering with a real binary is C-verify's measurement.
- **The server inherits the first leg's cwd and environment.** It is spawned with the command, working directory and environment of whichever session starts it first; sessions carry their own `location.directory` for API work, but a per-workspace `opencode.json`/`AGENTS.md` (and anything else OpenCode discovers from the server process's cwd) is therefore whatever that first workspace had. Per-workspace server configuration is unmeasured and not claimed; a task whose OpenCode setup differs per workspace should be checked in C-verify.
- **A dead server is a crash.** The driver's stream ends and its reconnect attempts fail, so the frontend reports `exited` with the reason in `Session.launchError`; starting the stopped session again starts a new server and rebuilds the conversation.

### The Codex driver (stage C, C3)

Codex is `both-live` the same way OpenCode is: one app-server owns the thread, and both frontends are clients of it. The difference is that the app-server is **one per session**, not one per Corral run, because the probe measured a second app-server refusing a thread another one holds (`thread <id> already has an active writer`), so a per-run server would have to fence sessions against each other for no gain.

- **One app-server per session, and the terminal is a client of it.** `CodexServers` (`apps/server/src/chat/codex-server.ts`) spawns `codex app-server --listen unix://<dataDir>/codex/<session>.sock` with the launch's working directory and environment, waits for the socket, and keeps a per-session record at `<dataDir>/chat/codex-server-<session>.json` (pid and `/proc` start time, written by `writer-claim.ts`). Both legs acquire the same server: the chat driver is a JSON-RPC client of the socket, the terminal runs `codex --remote unix://… resume <thread>`. The last leg stops it (SIGTERM to the group, then SIGKILL after the grace); a Corral that starts again stops a recorded server before spawning its own; a server that dies releases the record and notifies its clients, and the terminal's reconnecting TUI is closed with the session.
- **The unix listener is a WebSocket, and the driver uses `ws`.** Measured: `codex app-server --listen unix://PATH` answers a plain `GET` with `HTTP/1.1 101`, and the frames are the v2 JSON-RPC messages. `ws` addresses it as `ws+unix://<path>:/`, so no frame code is hand-written. `--stdio` is the newline transport, but it leaves nothing for a terminal to attach to.
- **Thread ids are the server's.** `thread/start` takes no id (checked in the generated 0.166.0 schema), so the driver reports the assigned id through the launch's `onAgentSessionId` and `Session.agentSessionId` stores it — for chat sessions only; terminal sessions keep rollout discovery. A rebuild is `thread/resume` (which also subscribes the connection to the thread's events, measured: an unsubscribed connection gets no item notifications from a `turn/start` it sent) plus `thread/read` when the resume carried no turns. An app-server that no longer has the thread (`no rollout found`) gets a new `thread/start`, and a thread the terminal created is adopted from `thread/list` — the server is per session, so the only non-ephemeral thread in it is ours.
- **The prompt is sent only into an empty conversation.** The rebuilt transcript decides, not a flag on the session row (C1's rule): a resume never repeats the task prompt. The user's item id travels as `clientUserMessageId` and is echoed in the item's `clientId`, so the rebuild replaces the optimistic item instead of duplicating it.
- **Mapping.** `turn/start` is a prompt, `turn/steer` (`expectedTurnId` + input) is steer — measured live, and its message appears as the same kind of `userMessage` item — and `turn/interrupt` ends a turn (`turn/completed` status `interrupted`). `item/started`/`item/completed` and the `item/…/delta` notifications become items: assistant text, reasoning, command executions (`aggregatedOutput`), file changes (each `changes[].diff` is unified diff text → `ChatDiff`), MCP calls and web searches. A `turn/diff/updated` covers a file-change item that carries no per-file diff. Follow-up is declared off: `thread/queue/add` is behind the app-server's `experimentalApi` capability (measured refusal), and the driver does not opt into that surface for one call.
- **Approvals, and the first answer wins.** The app-server asks each attached client with a JSON-RPC request (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, legacy `applyPatchApproval`/`execCommandApproval`). The driver turns it into a `select` user request whose option values are the decision strings that request offers (`availableDecisions`; the contract sends only a value the server named), answers with `{decision}` on that request id, and marks the item resolved when a `serverRequest/resolved` says another frontend answered first. It never passes an approval-policy or sandbox override: the thread uses the user's Codex config exactly as the terminal does, so approvals arrive when the config asks for them. A pending approval is lost on a frontend restart, like pi's dialogs.
- **The version is gated, and the terminal stays available.** The driver reads `codex --version` (cached per executable, and a failed probe is retried rather than cached) and refuses chat on anything but the measured `0.166.0` with a sentence naming both versions; the terminal launch checks the same answer to decide between the Corral app-server (`--remote`, both views live) and stage A's plain `codex` (its own daemon, chat refused for that run). The app-server is labelled experimental, so the gate is the contract, not a claim of compatibility.
- **The launch's model and provider open the conversation.** `thread/start` carries the same native `model`/`modelProvider` the terminal's `-m`/`-c` flags carry, so a chat-first session does not silently run the app-server's default. An approval offers only the decisions the request lists (`availableDecisions`); an object-valued decision has no plain-string form in the contract and is not offered, and the driver never sends a decision the server did not name. A recorded thread id stays resumable while its app-server is live, even before the first turn writes a rollout (the thread is in that process's memory); once the server is gone, an id with no rollout cannot be resumed, so the terminal starts a new conversation with the task prompt and the chat driver's `no rollout found` recovery starts a new thread and reports it. The rollout lookup uses the UUIDv7 thread id's own creation day, so a launch reads a day's directory rather than walking every day the home has.
- **Model and reasoning switching are declared unsupported**, so the client hides those controls; the session reports the thread's model and provider.

## Keyboard

Findings (sourced, see research notes below): browsers keep some chords for themselves, and Electron can capture almost everything.

- Prefix mode: prefix key, then an action key. Default prefix `alt+a`.
- Every binding is configurable in `~/.config/corral/config.toml` (`packages/protocol/src/config.ts`). The server reads and watches the file and pushes the effective config to every client; an invalid entry is dropped with a reported problem, the rest applies. User commands bound to keys (Herdr's `[[keys.command]]` popups) come after MVP.
- Direct chords are reserved for things that must work inside a terminal without the prefix. Font-size +/-/reset exists in the playtest prototype, not in Corral: terminal text is fixed and does not follow the interface text scale. Adding those controls is a separate scope.
- A command palette lists every action with its binding.
- Bindings match `KeyboardEvent.code` (physical key), so they work on the Russian layout; text input uses `key`. Printable and composing keys are never intercepted, so xterm.js IME and dead-key handling keep working.
- **Electron**: the app intercepts in `before-input-event` and has no application menu, so a lone Alt does not reveal a menu bar on Linux.
- **Browser**: Ctrl/Cmd+W/T/N, Ctrl+Shift+T and Ctrl+Tab are browser-owned in Chromium and Safari (Firefox lets some through); a page cannot cancel them. Default bindings avoid them, config validation warns when a user binds one, and a `beforeunload` prompt guards an accidental Ctrl+W in a terminal. Keyboard Lock unlocks them only in Chromium in JS-requested fullscreen; optional, not relied on.

## Stages

The MVP (server and desktop client, projects and tasks, terminal sessions, agent status and board, prefix keymap and palette) is built. Then, in order:

- **A. Task model on the terminal** (built, verified end to end): the shell revised per `layout.md` (task-only sidebar, task header, session tabs); a prompt-first new-task view replaces the form; the primary agent starts with the prompt; title (and optional slug) generation; readable worktree paths; no automatic shell; renaming a task; sidebar flat by status or grouped by project; task status with unread completion. - **C. More**: OpenCode and Claude Code drivers, then Codex; diff, commit and pull request linked to the task; links to local files, images and video in chat.

Later: mobile client (only constrained now by decision 14), remote servers, orchestration.

## Open questions

- **One PTY grid, several clients.** Each attached client adopts the server's grid, so a client that cannot show it is clipped until it refits: an attach or reconnect after the replayed snapshot, `focusin` in its terminal, a `visibilitychange` to visible, or a resize of its pane (theme: the stage A verifier's P2). A hidden client leaves the shared grid alone until it becomes visible. Options: smallest-wins on the server (tmux's default), a latest/focus policy with an explicit owner, or a per-client view of one PTY. Decide when a real multi-window workflow is scheduled; stage B only adds those refits and documents the limit.
- **Mobile shell**: Capacitor (reuse the web client in a WebView) vs Expo with DOM components for the terminal. Either keeps the server API; decide when mobile starts. xterm.js WebGL context loss on mobile needs testing (Orca hit it).
- **Live PTYs across server upgrades** (after MVP). Prior art: Orca keeps a versioned daemon per protocol version and lets old daemons keep their sessions; Herdr hands PTY master fds to the new server over a Unix socket (`SCM_RIGHTS`) and rolls back on failure (`.refs/herdr/src/server/headless/lifecycle.rs`). For us: either a tiny, rarely-changing PTY-holder process separate from the server logic, or Herdr-style fd handoff (Node needs a native helper for that).
