- **Stage B · T0 — the refit trigger is the terminal host, not the document.** `focusin` on the host plus `visibilitychange` to visible, rather than a document or window `focus` handler: a page that regains focus must refit the one terminal that got the keyboard, not every mounted terminal, and the host trigger is the only one a browser test can attribute between two clients. The debounce and mount fit are unchanged, so a client that opens unfocused still takes its first fit. Code: `apps/web/src/modules/terminal/terminal-view.tsx`; the remaining shared-grid limitation is in `design.md` **Open questions**.
  Decisions an autonomous run made on the user's behalf: question, options, choice, why, where in the code. The user reviews them; they never block a run.

- **Stage A · A3 — starting the primary session again re-offers the task's prompt.** A2 left it to the caller whether a start that finds no conversation to resume hands the prompt over again. Choice: yes, for the task's primary session only, decided on the server (`SessionService` → `#taskPrompt`, design.md **Sessions**), because the prompt is the task's work and only a launch that never reached the agent gets it — a real resume still drops it. This covers a user restart and a restore after a server restart (a review finding: the restore used to lose the prompt and leave the session marked running without it). The session row a failed create leaves behind (`stopped` with its `launchError`) is what makes the user restart recoverable. Tests: `tasks-rpc.test.ts`, both directions with the fake claude agent.

- **Stage B · B1 review rounds 1–2 — "one writer" is claimed and proven, not hoped for.** Three rules make it structural: a `ChatService` launch claims its session id synchronously before awaiting the previous writer, so a second launch of that id is refused instead of racing to `spawn` (`chat-service.ts`, pinned by a `Promise.allSettled` test that used to produce two children); session relaunches go through the same `SerialQueue` as start/stop/restart and are awaited inside `resumeAllIn`, so a restore cannot spawn beside a queued stop or resurrect a session the user stopped (`session-service.ts`); and a writer record carries the process's `/proc/<pid>/stat` start time beside its pid, so a reaped and reused pid is left alone, an unidentifiable live pid refuses the launch rather than being guessed at, a record from before the last boot is never killed whatever identity it names, and a refused launch keeps the record so the next attempt refuses again (`writer-claim.ts`). A cursor from a replaced frontend also cannot replay, for every watcher and across a server restart: each launch reserves and persists a sequence block in `<dataDir>/chat/<session>.floor.json` before it spawns, so the next timeline always starts above every cursor any client could hold from an earlier one, and a cursor below the start is a hole answered with a snapshot (`sequence-floor.ts`, `timeline.ts`, `chat-service.ts`). Supervision is exercised with a fake pi that ignores stdin EOF and keeps a `sleep` in its group, and with its `silent` mode for the ready deadline.

- **Stage B · B1 — pi exits on stdin EOF mid-turn, measured; the pid record still guards the restart.** Closed stdin 1.5s into a slow turn on pi 1.4.0 with the real binary: the process exited with code 0 about 16ms later, without finishing the turn. - **Stage C · C5 — detection is syntactic and pure; resolution is what decides a link.** Options: one function that checks the filesystem, or detection over the text plus a batch lookup. Choice: `detectLinks` (`apps/web/src/modules/chat/local-links.ts`) finds URLs and path-shaped tokens with their `:line[:col]`, and `files.resolve` answers existence per candidate; the renderer's anchor shows a link only for a resolved file, so `src/foo` that does not exist stays text and a path never needs a dead click to reveal itself. Why: detection has to run on every streaming delta and be testable without IO (property tests: no throw on odd input, tokens within bounds, and an appended chunk never rewrites a settled token), while existence is the server's fact. The Markdown transform deliberately does not consult the answer, so a late resolution re-renders the anchor instead of re-parsing the message. Recorded in `docs/ux.md` (**Local links in chat**). Code: `local-links.ts`, `local-links.tsx`.
- **Stage C · C5 — an ordinary web link leaves the capability-bearing window through the shell's own IPC, and in a browser it opens a tab.** Options: let the anchor navigate and rely on `will-navigate`/`setWindowOpenHandler`, or give the page an explicit `corral:open-external` request. Choice: explicit, over the existing narrow preload bridge, with the shell re-validating the scheme (`packages/protocol/src/external-url.ts` is the one rule, shared with the desktop's navigation guard); browser mode calls `window.open(url, "_blank", "noopener,noreferrer")`. Why: `docs/design.md` **Local trust boundary** already says such links never load in this window, and one explicit call is observable — a browser test pins the bridge call, the tab and an unchanged location, and the Electron e2e records `shell.openExternal` in the main process. Code: `apps/web/src/modules/chat/local-links.tsx` (`openWebLink`), `apps/desktop/src/{main,preload,bridge}.ts`, `packages/protocol/src/desktop-bridge.ts`.

- **Stage C · C1 — the OpenCode server inherits the first leg's cwd and environment.** `opencode serve` is spawned with the command, working directory and environment of whichever session needs it first. Per-workspace server configuration is unmeasured; a task whose OpenCode setup differs per workspace is C-verify's check.
- **Stage C · C1 — one `opencode serve` per Corral run, started lazily and stopped with its last client.** Options: one server per task workspace, one per agent session, or one per run. Choice: per run. Why: a session carries `location.directory` and `POST /api/session` accepts a caller-chosen id, so one server serves every workspace and every session of the run; a server per session would pay a process and a password per session and give the terminal nothing to attach to; a server per workspace would leave two servers when a task moves between worktrees. It starts with the first session (chat or terminal) that needs it and stops when the last leg releases it; a server that dies is a crash, not a restart. Code: `apps/server/src/chat/opencode-server.ts` (`OpenCodeServers`), `apps/server/src/transport/server.ts`, `apps/server/src/sessions/session-service.ts` (`#openCodeServer`, both legs). Pinned by `opencode-server.test.ts` and `opencode-rpc.test.ts` (two sessions, one `serve`; last stop ends it).
- **Stage C · C1 — the shared process is recorded once, keyed by the process.** Options: keep C0's per-session `writer` record for the server too, or add a process-keyed record. Choice: the process-keyed record at `<dataDir>/chat/opencode-server.json` (pid + `/proc` start time, written by `writer-claim.ts`), released by the last client. Why: per-session records for one pid would let the next launch of session A kill the server session B uses, and the first stop would forget a process that still runs; one record also makes a restarted Corral stop the previous server before spawning its own, so a second server on one data directory is never left running. The TUI leg is a client of the same record, so the one-writer rule covers both legs. Code: `opencode-server.ts`, `writer-claim.ts`; `ChatDriverLaunch` grew `agentSessionId` and an optional `server` address (server-side only, no wire change).
- **Stage C · C1 — OpenCode's loopback server is the trust boundary, with `OPENCODE_SERVER_PASSWORD` and HTTP Basic.** Options: add a Corral capability token, rely on loopback only, or use OpenCode's own password. Choice: OpenCode's own. Measured on 2.2.5: the default bind is `127.0.0.1:4096`, `/api/*` answers 401 without credentials, and `curl -u opencode:<password>` is the accepted form; `OPENCODE_SERVER_PASSWORD` is read by both the server and its clients. - **Stage C · C1 — session ids stay Corral's, including across a server restart.** Options: adopt the id `POST /api/session` generates, or send `Session.agentSessionId`. Choice: send it, and re-create the session under that id when a restarted server does not know it. Why: settle/continue/restart/resume and the terminal's `--session` then all name one conversation; adopting would make every restart a new id and break the handoff. Measured: `POST /api/session` accepts `{"id":"ses_…","location":{"directory":…}}`; `opencode-rpc.test.ts` kills the server and restarts the session, asserting the same id and a transcript rebuilt from `GET /api/session/:id/message`. - **Stage C · C1 — steer and follow-up are `delivery: "steer" | "queue"`; a prompt while a turn runs is refused.** The plan's inferred `delivery` field is real and its enum is `steer | queue` (read from `/openapi.json` on the running 2.2.5 and from the embedded client); the prompt response also defaults to `steer`. Model and reasoning switching are declared off rather than faked. Code: `apps/server/src/chat/opencode-driver.ts` (`send`), `opencode-projection.ts`.
- **Stage C · C1 — the plugin no longer loads for a server-backed OpenCode session; the terminal view's status is OSC 7501.** Options: keep loading the plugin into the shared server, or drop it for server-backed sessions. Choice: drop it.
