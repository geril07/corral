**No paid dependency.** A dependency the project must pay for is not added: Corral has to run for someone who has not bought anything. A proprietary but free-of-charge package is allowed, and its licence is recorded in the toolchain table above.

C3's Codex app-server is **one per session** (`apps/server/src/chat/codex-server.ts`), recorded at `<dataDir>/chat/codex-server-<session>.json` with the same pid-and-start-time shape: the chat driver and the terminal leg (`codex --remote unix://…`) are its two clients, its socket is the launch's `socket`, and the thread id it assigns reaches the session row through the launch's `onAgentSessionId`, because `thread/start` accepts no caller id. The version both legs are gated on is read in `apps/server/src/agents/codex-version.ts` (`TESTED_CODEX_VERSION`), cached per executable; the terminal falls back to the plain `codex` launch for an untested one.

Commands are root scripts over `vp`: `pnpm check` (format check, lint, type check, Node tests), `pnpm test:browser`, `pnpm test:e2e`, `pnpm dev`. `pnpm dev` runs against the checkout's own `.dev/` state, data and config directories (`scripts/dev.mjs`), so a development server cannot take the single-instance lock, database or config file from a packaged app; `pnpm dev:desktop` runs Electron against the same directories and the running web dev server, and the installed app keeps the XDG defaults. `pnpm dev` also prints the page URL, capability included, each time the server publishes its endpoint, so a `node --watch` restart hands out a fresh link instead of leaving a stale tab; that link is the dev page's only source of the token, which is already readable in `.dev/state/endpoint.json`, and the desktop page still never takes one from a URL. `pnpm dev --fake-agents` puts the fake agent CLIs first on the dev server's PATH, and `pnpm seed` then
fills a fresh `.dev/` with a fixture repository, a project, a chat transcript, a shell session and a
settled task, so a UI review has real states to photograph without a login or a model call; run the
pair once per fresh `.dev/`. Vitest has two projects: `node` (every `*.test.ts`, forks pool) and
`browser` (`apps/web`, `*.browser.test.tsx`).

## Repository layout

```
apps/
  server/     long-lived server: PTYs, tasks, sessions, git, status, RPC + terminal sockets
  web/        React client (runs in Electron and in a browser)
  desktop/    Electron shell: window, starts/finds the server, loads web
packages/
  protocol/   wire contracts: zod schemas, oRPC contract, terminal stream messages, chat shapes, protocol version
  client/     framework-agnostic client runtime: RPC client, terminal stream client with acks,
              reconnect, stores; shared by web now and mobile later
docs/
```

Dependency direction, enforced by lint (import boundaries):

- `protocol` depends on nothing internal.
- `server` → `protocol`. `client` → `protocol`. `web` → `client`, `protocol`.
- `desktop` → `protocol` (the server endpoint file contract only); it starts the server and loads the web bundle.
- Nothing imports `server` except tests. Its own tests import it normally; tests of `client` and `web` start the real server through a relative import (`packages/client/test/server-fixture.ts`, `apps/web/test/real-server.ts`), because a package dependency would be a cycle (`server` already uses `client` in its tests). A client never reaches into server code for types; shared types live in `protocol`.

**Two directories, two keys.** The single-instance lock keys on the state directory while the database and the chat writer records key on the data directory, so two servers started with one data directory and different state directories would pass the lock and share the database and the per-session writer records. One machine, one state directory, is the supported shape.

Internal packages export TypeScript source (no build step). The server runs that source directly in Node, so all code is restricted to erasable TypeScript (`erasableSyntaxOnly`: no enums, namespaces or parameter properties) and relative imports carry `.ts` extensions. The production server is bundled into one file with `vp pack`. Verified: Node 26 runs the server from source, including workspace packages reached through pnpm symlinks.

## Code organization

- **By domain, not by layer.** Every top-level folder under `apps/server/src` is a domain (tasks, sessions, terminals, chat, changes, …); each owns its logic, its IO and its tests.
- **Pure logic apart from IO.** State transitions and parsing (task status from agent reports, OSC 7501 parsing, keymap resolution, session switching rules) are plain functions over plain data. IO (node-pty, SQLite, git, sockets) sits in thin modules that call them.
- **Thin transport.** RPC handlers validate input, call a domain function, map errors. No logic in handlers.
- **A git read cannot write the repository.** Every git call that only reads a task's workspace goes through `gitRead` (`apps/server/src/git/git.ts`), which sets `GIT_OPTIONAL_LOCKS=0`, `diff.autoRefreshIndex=false` and `GIT_LITERAL_PATHSPECS=1`: `status` and `diff` refresh `.git/index` by design, and the changes read model must not; a path such as `*.txt` is a file name, not a glob. `git()` closes stdin and bounds both time and output, each mapped to a `GitError`, so a helper or a `textconv` driver cannot hold an RPC open; diffs also pass `--no-ext-diff --no-textconv`. Untracked files are counted and patched from a bounded prefix, never read whole.
- **Stores in `packages/client` are framework-agnostic** (subscribe/getSnapshot); React reads them with `useSyncExternalStore`. Mobile reuses them as is.
- **Terminals stay imperative.** Output goes from the stream client straight into `terminal.write()`, never through React state.
- **Names are concrete.** No `utils`, `helpers`, `common`, `misc` (Orca's rule): a module is named after what it does.
- **File bytes for chat's previews travel over RPC, and the workspace is the allow-list.**
  `apps/server/src/files/` owns it: `resolveWorkspaceEntry` (`file-access.ts`) resolves the task's
  workspace and the requested path through `realpath` and refuses what the workspace does not
  contain with `FILE_OUTSIDE_WORKSPACE`; `FilesService` is the only reader — `files.read` is
  bounded by `FILE_PREVIEW_LIMITS` and `files.openEditor` runs `[editor] command`/`$VISUAL`/`$EDITOR`
  as a terminal in that workspace. There is no HTTP route and no range request, so the bytes cross
  the same authenticated channel as every other call. **The read is anchored to the checked
  inode**: resolving and reading are two moments, so `readVerifiedBytes` (`verified-read.ts`) opens
  the resolved path with `O_NOFOLLOW`, `fstat`s the handle, requires the `dev`/`ino` the resolving
  `stat` returned and bounds the bytes it reads from that handle — a symlink planted or a file
  swapped after the check is `FILE_CHANGED`, not served. `..` is normalised lexically before
  `realpath` (`link/../x` is `x` beside `link`), which the resolver states and a test pins.
- **A chat resume is asked for only when the conversation exists.** `chatLaunchHow` (`session-service.ts`) mirrors the terminal leg's check: `how: "resume"` becomes `"start"` unless `AgentAdapter.hasConversation` proves the agent's conversation is on disk. It matters for Claude, which writes no transcript before its first prompt: a task created with no prompt, `prefix v` to the terminal and back, and a restart after a refused launch all reach a chat launch with an id and no conversation, and an SDK `resume` of a missing id fails with "No conversation found" instead of starting. The same id is kept, and the driver then sends the task prompt exactly once.
- **Claude's driver is the one configured by an SDK, not spawned by argv.** `apps/server/src/chat/claude-driver.ts` implements C0's `ChatDriver` over `@anthropic-ai/claude-agent-sdk`, and `claude-projection.ts` maps the SDK's stream and the transcript into the contract. The SDK seam is `ClaudeSdk` (`query` + `getSessionMessages`), which the tests replace with `apps/server/test/fake-agents/fake-claude-sdk.ts` — a real `claude` turn needs the user's login, so no suite runs one. `Options.sessionId` is Corral's UUID on a start and `Options.resume` is `Session.agentSessionId` on a resume, `getSessionMessages(id)` rebuilds the transcript before the live frames are applied (no `dir`: the project-directory slug is not ours, and a narrowed read can answer `[]` for a conversation that exists, as the terminal leg's whole-tree search already assumes), and the task prompt is handed over only when that transcript has no user message. `canUseTool` (with `permissionMode: "default"`, never `bypassPermissions`) becomes one `select` user request named after its `toolUseID`; an answer resolves that one promise, and an expired, interrupted or stopped request is denied so the CLI is never parked. `Query.setModel`/`applyFlagSettings({ effortLevel })` back `chat.setModel`/`chat.setReasoning`, with the lists from `supportedModels()`. `spawnClaudeCodeProcess` is the SDK's documented hook: the driver spawns the CLI in its own process group there, records its pid as the session's writer (so a restarted server or a terminal handoff stops it before a second writer exists) and kills the group when a stop has to. `claude --resume <id>` is the terminal leg; the view is `handoff-only`. Two measured limits are load-bearing: the CLI emits `system/init` with the **first turn**, so preparation (`supportedModels()`, the transcript) starts at launch and the prompt is not gated on init; and the in-process `getSessionMessages` reads `CLAUDE_CONFIG_DIR` from the server's own environment, so a launch environment that points it elsewhere is refused the prompt (`historyIsReadable`) rather than risking a duplicate. |
- **The local capability is part of the transport contract.** `ServerEndpoint` carries the per-run capability; clients take a `ServerTarget` and present it as a WebSocket subprotocol (`packages/protocol/src/handshake.ts`). Desktop re-reads the endpoint file for every preload IPC request and clients ask for the current `ServerTarget` before each reconnect, so a restarted server is picked up without an app restart. Browser/dev stores the URL and capability together and only reuses the pair for the same server URL (`packages/client/src/bootstrap.ts`). Never append the capability to a URL or log it.
- **A migration step may be a function, and a step that adds a column must check first.** `MIGRATIONS` (`apps/server/src/storage/database.ts`) holds SQL strings and `(db) => void` steps, each run in its own transaction; `ALTER TABLE` has no `ADD COLUMN IF NOT EXISTS`, and a development database can already be shaped like the target (C6's own round 2 edited migration 11 in place), so such a step reads `table_info` through `tableHasColumn` before it writes. Never edit a migration that shipped; when one is edited inside an unreleased branch anyway, the following step must be idempotent.
- **Protocol changes are versioned.** Client and server exchange `PROTOCOL_VERSION` on connect and refuse a mismatch; new fields are optional within a version, but a release barrier bumps the version when an older daemon would silently ignore them (version 3 adds launch profiles/model fields; version 4 adds the settings action and its exhaustive bindings key; version 5 prevents older daemons stripping task-source inputs; version 6 adds the task title source, the rename-task/session-number actions with their exhaustive bindings, and the required task/naming/project settings; version 7 adds the sidebar-mode action, the server-owned task `seenAt` and the task's prompt and primary session; version 7 never left the trunk, so the task's new required fields joined it instead of waiting for a version of their own; version 8 adds the toggle-sidebar action and its binding; version 9 adds the `chat.*` contract, `Session.view` (optional until B1's migration), `sessions.setView`, the abort-turn/change-model/change-reasoning/switch-view bindings, `[tasks] view = "chat"`, `[agents.<kind>]` with its `AGENT_DISABLED` refusal, and `ConfigState.agents`; version 10 adds the per-agent capability record in `chat.capabilities` — `kind`, `steer`, `followUp`, `approvals`, `modelSwitch`, `reasoningLevels` and `terminalView` (`both-live | view-only-terminal | handoff-only`) — which a version 9 daemon answers with a bare driver list, so its reply is refused rather than read as drivers that declare nothing; 10 also grew the read-only `changes.*` contract (`changes.watch` for every task's changed files, `changes.files` to recompute one, `changes.diff` for one capped file diff) and the `changes` action with its binding, which a daemon from before C4 answers with an unknown procedure — the client's own defaults supply the binding, and the Changes tab says that this server does not offer changes).; 10 also grew C5's `files.*` procedures (`resolve`, `read`, `openEditor` — chat's local links) and `ClientConfig.editor` (`[editor] command`), both optional for a daemon already on 10, because an older 10 answers the procedures as unknown and a client reading an absent `editor` falls back to `$VISUAL`/`$EDITOR` as the server does; and 10 grew C6's write path — `changes.finish` (the branch, base, push remote and staged paths a confirmation names), `changes.stage`, `changes.commit`, `changes.push`, `changes.createPullRequest` and `changes.pullRequest` — whose typed refusals (`CHANGES_REMOTE_MISMATCH`, `CHANGES_NO_REMOTE`, `CHANGES_BRANCH_MISMATCH`, `CHANGES_NOTHING_STAGED`, `CHANGES_EMPTY_MESSAGE`, `CHANGES_PUSH_REQUIRED`, `CHANGES_CLI_MISSING`, `CHANGES_AUTH_REQUIRED`, `CHANGES_CLI_FAILED`, `CHANGES_RESPONSE_INVALID`) a daemon from before C6 does not know: it answers the procedures as unknown, and the Changes tab says the action is unavailable there instead of pretending it ran; version 11 requires the shared `models.watch/save/catalog` contract on every client, and version 12 adds the focus-sidebar action and its binding; version 13 requires `projects.directories` before project registration; version 14 adds the required `Project.defaultBaseBranch`/`pinnedAt`, nullable task project/branch/workspace ownership, the model policy's `providerOrder`/`modelOrder`, and `projects.baseRefs` (a version 13 daemon's model policy lacks the order arrays `orderModels` reads, so its replies are refused rather than crashing the client).
- **A git write is only a confirmed action.** `git()` without the flags the read rule above sets is the write path, reached only from the Changes tab's explicit actions. `apps/server/src/git/writes.ts` owns the three: `stagePaths` (`git add --all -- <paths>` / `git restore --staged -- <paths>`), `commit` and `pushBranch` (`git push --porcelain -- <remote> refs/heads/<branch>:refs/heads/<branch>` — never `--force`, never `--delete`, and no `--set-upstream`). The remote is the checked-out branch's configured remote, else `origin`, else the only remote (`resolvePushRemote`, `apps/server/src/git/remotes.ts`); a write carries the confirmed remote name **and URL** back, and the server re-reads the URL and refuses a mismatch before git runs.
- **A child process is bounded by its exit and its process group, not by its pipes.** `apps/server/src/process/run-process.ts` is the one spawner under `git()` and the native CLIs: `spawn` in its own process group, a deadline that kills the group (so a `pre-push` hook or a wrapper's helper dies with it), output bounded while it arrives, stdin closed or filled, and settlement on the child's **exit** with the pipes destroyed after a short drain. Waiting for `close` (which `execFile` does) hands the call's duration to whichever grandchild inherited the pipes; measured, a 2 000 ms CLI call resolved at 30 011 ms that way. `git.ts`, `native-cli.ts` and the naming runner (`naming-run.ts`) all go through it and map its `ProcessFailure` onto their own errors and wording — one spawner, so a deadline and a process group mean the same thing everywhere.
- **Every remote write names the push destination, and `--repo` names the repository.** `git remote get-url --push` (expanded through `insteadOf`) is the confirmed destination: `ChangesRemote.url`, the mismatch check and `git ls-remote` all use it, because `remote.<name>.pushurl` is where a push really goes. `gh`/`glab` get `--repo` from the remote's **configured** URL (`remote.<name>.pushurl`, else `.url`, unexpanded), so a local `insteadOf` alias still points the CLI at the confirmed forge repository; the row keeps that repository with its host (`PullRequest.repository`, e.g. `forge.example/acme/app`, optional on the wire) for its refreshes. No `--repo` for a local-path remote, where the CLI resolves its own.
- **A read with `--repo` also names the request.** `gh pr view --json … --repo OWNER/REPO` is refused by `gh` ("argument required when using the --repo flag", probed in `apps/server/test/contracts/gh-pr-argv.contract.ts`), so `changes.pullRequest` and a create's follow-up read pass the number positionally — from the stored row on a refresh, from the URL `pr create` printed otherwise — and a read without `--repo` keeps the CLI's own current-branch lookup. The fake answers any argv, so only the contract test can police an argv the CLI rejects outright.
- **Native forge CLIs have one runner.** `apps/server/src/cli/native-cli.ts` runs `gh`/`glab` (the shared spawner above, stdin closed or filled, no pager or prompt or debug output, the other vendor's tokens dropped) and classifies its failures; `apps/server/src/issues/issue-import.ts` and `apps/server/src/changes/pull-request.ts` map those to their own typed errors, so the two cannot drift on what a CLI call inherits. `gh pr checks` exits non-zero when checks fail or are pending, so a pull-request read uses the runner's tolerant form for that one call.

## Model catalog and preferences

`models.watch/save/catalog` shares per-tool/instance preferences between clients.
`apps/server/src/models` owns revision-checked atomic `models.toml` writes and lazy scoped metadata
caches. The file sits beside the launch config so preference edits cannot rewrite its unrelated
values or comments; SQLite is not a second preference authority. Revisions track policy content,
including external file edits, rather than a counter the user must maintain by hand.
Native pi/OpenCode lifecycles reuse the driver/server supervisors with metadata-specific process
claims, never the working session. `packages/client` watches shared preferences; Settings and every
picker apply the pure protocol visibility projection. Lifecycle, budgets and limitations:
[Model catalogs](model-catalog.md).

## Web UI kit

Protocol 14 requires `projects.directories`, a bounded authenticated read of the server filesystem
before registration. It scans at most 4096 entries and returns at most 200 folders, marking an
incomplete listing. It never runs Git. Canonical registration remains `projects.add`.
`projects.baseRefs` answers what a new worktree can start from — local branches, checked-out ones
included, then remote-tracking refs — while `projects.branches` keeps its checkout meaning and
hides a branch another worktree holds.

shadcn/ui Base UI / Nova components live in `apps/web/src/common/ui`.
The OpenCode-based visual shell supersedes the earlier T3-like appearance for the workspace; its
semantic roles and Corral chrome metrics live in `common/ui/visual-shell.css` with the MIT/OFL
notice beside it. Modules must use kit variants instead of class/style overrides on controls. The
AST gate covers imported aliases, namespaces, field/command wrappers and opaque prop spreads.
Provenance, token mapping and intentional adaptations: [`ui-kit.md`](ui-kit.md). Modules compose
the kit; they do not import Base UI, cmdk or icons directly. Keep the UI-boundary lint and
class/token gates active.

Chat Markdown is **Streamdown 2.7.1** (Apache-2.0); its code highlighter and the diff renderer are
the one shared **`@pierre/diffs` 1.6.2** instance (Apache-2.0), not `@streamdown/code`'s second
Shiki (goal D1). The timeline is virtualized by **`@legendapp/list` 3.7.1** (MIT). All three are

## Testing

Philosophy: test observable behavior through real dependencies. Fakes only where the real thing is expensive or nondeterministic.

| Layer              | What                                                                                                                                    | Tool                                                                                                                 | Where                                                     |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Unit               | Pure logic: parsers, state transitions, keymap                                                                                          | Vitest; fast-check (`fc.assert`) for parsers                                                                         | `*.test.ts` next to code                                  |
| Server integration | Domain behavior through real SQLite (temp file), real PTYs, real git repos (temp dir), real WebSocket server on port 0, fake agent CLIs | Vitest, `pool: 'forks'`                                                                                              | `*.test.ts` next to code; fixtures in `apps/server/test/` |
| Browser            | Components and xterm integration in real Chromium, real keyboard events                                                                 | Vitest Browser Mode + Playwright provider                                                                            | `*.browser.test.tsx`                                      |
| End to end         | Desktop app against a real server; web client in a browser against a real server                                                        | Playwright (`_electron`, experimental); locally in a private headless sway (`scripts/headless.sh`), Xvfb on Linux CI | `apps/desktop/e2e/`, `apps/web/e2e/`                      |
| Agent contracts    | Real agent CLIs still behave as the fakes assume (flags, OSC 7501, session ids, pi's RPC protocol)                                      | Vitest, opt-in (`pnpm test:contracts`), not in CI                                                                    | `apps/server/test/contracts/`                             |

**The browser suite runs in four native shards.** `pnpm test:browser` is a Vite Task graph: four `vp test run --config vite.config.ts --shard=i/4` processes started from `apps/web` (the package config is their root because the workspace root's `projects` routing does not carry a custom sequencer). Each process has its own Vitest `globalSetup`, so each shard gets its own real server, `CORRAL_CONFIG_DIR` and git repos; inside a shard the files still run one at a time against that server. That is why sharding is safe where lifting `fileParallelism: false` is not. `BROWSER_SHARDS` in the root config is the single shard-count definition. Before the shards start, a serial `browser-warm` task collects every browser test file with a test-name filter that runs none, so Vite's dependency optimizer fills the one shared cache first; otherwise four cold processes optimize into it together and race on the same deps rename. Each shard depends on that pre-pass, which makes a cold `pnpm test:browser` supported, and no user-facing shard or cache option exists. `WeightedShardSequencer` reads `apps/web/test/shard-weights.json` (keys relative to `apps/web`) and places whole files on the least-loaded shard, longest first; a file outside the table gets the median recorded duration until its own weight is added, and still participates in the assignment. The task's `cache: false` is per task because that is the one cache control a CLI flag cannot override. `pnpm test:browser` pins four concurrent tasks; `vp run browser-shard-N` runs one shard through the same weighted path and its warm pre-pass, `pnpm exec vp test run --project browser` runs the suite in one process, and single-file debugging is `pnpm exec vp test run --project browser <file>`.

Weights come from a warm single-process JSON report: `pnpm exec vp test run --project browser --reporter=json --outputFile=/tmp/browser.json`, then write each `testResults[].name` relative to `apps/web` using `endTime - startTime` seconds. A cold run is not a baseline; a missing file gets the median and can move other files between shards.

**Fake agents** are small executables on `PATH` named `claude`, `codex`, `pi`, `opencode`. A script decides what they print (including OSC 7501), what input they wait for, and when they exit, and they log the arguments they were called with. They run in a real PTY. The fake `pi` also speaks RPC mode (`--mode rpc`): strict JSONL, one scripted turn with text deltas, an `edit` tool call carrying pi's unified patch, and a `confirm` dialog that waits for the client's answer, plus `crash`, `slow`, `badline` and `silent` modes and a per-session journal so a resumed process answers `get_messages` like pi does. Contract tests keep them honest against the real CLIs; `pi-rpc.contract.ts` starts a real pi against a local stub endpoint on port 0, with an isolated agent directory and no paid call.

Guidelines:

1. Test behavior a user or caller can observe, at the lowest layer that catches the regression. Extend an existing test before adding a new one.
2. Do not mock our own code or types we do not own. Use the real SQLite, PTY, socket, git and filesystem in temp dirs.
3. Fake only expensive or nondeterministic externals: agent CLIs (fake executables), paid APIs, and time or randomness when they are the behavior under test.
4. Never wait with a bare sleep. Wait for an observable signal (output, event, exit, readiness line) with a deadline.
5. Every test cleans up what it started: PTYs, process trees, sockets, temp dirs, also on failure.
6. Servers in tests listen on port 0 and report the assigned port; each test gets its own data directory.
7. Keymap tests send real key events (Browser Mode) and assert on `KeyboardEvent.code` and modifiers.
8. Parsers get property tests: output does not depend on chunk boundaries; malformed input never throws or hangs. Keep failing seeds as regular tests.
9. Visual assertions (screenshots) only in a pinned browser and OS environment.
10. Native-module suites run in forks. No retries by default; a test that passes on retry is a bug to fix, not a pass.
11. A test that restates the implementation is deleted, not maintained.

### Iterating versus gating

The full suites are the evidence; they are not the edit loop. Costs on this machine: `pnpm check` ~30 s, `pnpm test:browser` ~1m50s warm (109 s) and ~1m54s cold, including the serial `browser-warm` pre-pass and four native shards under the current workrun budget; `pnpm test:e2e` ~15 s, `pnpm test:contracts` ~6 s.

- While changing a file, run only what that file can break: `pnpm exec vp test run src/modules/chat/chat-rows.test.ts` (Node), `pnpm exec vp test run --project browser src/modules/chat/chat-view.browser.test.tsx` (one browser file), or the contracts file directly. A Node-only run is seconds; a single browser file is ~10–15 s.
- Before a slice is integrated, run the full gate the plan names (`pnpm check`, plus `pnpm test:browser` for web slices and `pnpm test:e2e` for user-visible flows) — once, on the final tree. A targeted run is never the evidence for a slice.
- **Targeted runs do not prove isolation.** Files within one browser shard share one real server and each test tears down what it created; a test can pass alone and fail in the suite when another file leaves state behind. That happened in stage B: four chat tests left a task on the shared server and a tasks test timed out two files later, invisible to single-file runs. Any file you add or change must be seen green in at least one full run.
- Chasing a flake: state the hypothesis before the second reproduction; if it passes alone, the next full run is a hypothesis test, not a retry. Do not compare against a base commit with only half the change reverted — the control is void. Budget the hunt: a P3-class flake may be recorded with a reason instead of fixed. Under load, a 15 s Vitest timeout is itself the failure mode, so check for competing heavy suites before believing a red run.
- On the Linux agent host, [Corral's workload policy](workrun.md) owns workrun entrypoints, group and heavy classification; [orchestration](workrun/orchestration.md) owns concurrent assignments and teardown. Generic CLI/resource semantics are in the [tool documentation](../scripts/workrun/README.md). Launcher changes also need the [real-systemd suite](workrun/testing.md).

## Documentation

Docs hold durable rules and decisions: what is true of the code after this change and would still be true next year. Volatile facts — commit SHAs, gate counts, which reference checkout a study used, local paths — go in the issue, the pull request or the commit message, where they are read once and then outlive their usefulness. A measured number belongs in a doc only when the code depends on it (a version gate, a cap, a timeout), and then the doc says what depends on it.

## Open

- **Shipping the server.** Proposed: ship an official Node binary with the app and, on first start of a version, copy it with the bundled server and node-pty into a versioned directory outside the install tree (`~/.local/share/corral/server/<version>/`), then run it from there detached. Why: dev, tests and production run the same Node (Electron 45 embeds Node 24, we develop on 26); node-pty needs no Electron ABI rebuild; the `runAsNode` fuse can be turned off; an app update cannot delete files under a running server (Orca hit this on Windows and relocates the same way). `utilityProcess` is out: it cannot be detached. Not verified: AppImage and macOS bundle behavior during an update with the old server still running.
- **Server/app version skew** after an update: the handshake refuses a mismatch; who stops the old server and when is still to be designed.
- **Server bundling and the OpenCode plugin.** `apps/server/src/status/opencode-integration.ts` reads the plugin file relative to its own module; bundling the server with `vp pack` must copy it or inline it.
